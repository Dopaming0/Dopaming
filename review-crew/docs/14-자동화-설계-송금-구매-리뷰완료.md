# 14. 자동화 설계 — 송금 · 구매 · 리뷰 완료

목표: 1인 운영에서 반복 작업을 최대한 자동화한다. 단, **"판단·검수·법적 책임이 걸린 지점은 사람이 최종 승인"**을 지키고, 자동화는 그 앞뒤의 기계적 작업만 맡는다.

먼저 결론부터: **완전 무인 자동화는 이 사업에서 불가능하고, 시도하면 위법·계정정지 리스크가 커진다.** 현실적 최적안은 **"스크립트가 준비 → 사람이 원클릭 승인"의 반자동**이다. 아래 3개 영역으로 나눈다.

---

## A. "구매" 자동화 — 먼저 경계부터

"구매"가 무엇을 의미하는지에 따라 완전히 갈린다.

### A-1. 배송형 체험단의 제품 발송 (✅ 합법 · 자동화 대상)
셀러 캠페인의 기본형은 **셀러가 리뷰어에게 제품을 무상 발송**하는 것이다. 여기서 자동화할 것:
- 선정자 배송지 취합 → 셀러에게 전달할 **배송 리스트 자동 생성**(구글시트에서 선정자만 필터 → 이름·연락처·주소·옵션 CSV 출력).
- 송장번호 회수 → 리뷰어에게 "발송되었습니다" 알림 문안 자동 생성.
- 리뷰어는 **돈을 쓰지 않는다.** 구매 행위가 없으므로 리스크도 없다.

### A-2. 리뷰어가 직접 구매 후 대금을 환급받는 "실구매 리뷰단" (❌ 위법 · 자동화 불가)
쿠팡·스마트스토어에서 리뷰어가 **실제 구매 → 별점/구매평 작성 → 업체가 상품대금을 송금(환급)**하는 모델. 이걸 자동화해 달라는 요청이라면 **할 수 없다.**
- 표시광고법 위반(대가 미표시 기만) + 플랫폼에 대한 **위계에 의한 업무방해**로 광고주·중개업자 모두 형사처벌 판례 다수.
- 송금을 자동화할수록 "조직적·반복적 범행"의 증거가 남아 양형이 무거워진다. **자동화가 오히려 독이 되는 유일한 영역.**
- 대안은 이미 킷 전체에 반영: 쿠팡 상품평은 **쿠팡 공식 체험단**, 스마트스토어 구매평은 **스토어 공식 리뷰 이벤트(포토리뷰 적립금)** 세팅으로만. 이 두 공식 기능은 플랫폼이 정산·표시를 알아서 처리하므로 "구매·환급 자동화"를 우리가 만들 필요 자체가 없다.

> 정리: 자동화할 "구매"는 **A-1(배송 리스트 자동화)**뿐이다. A-2는 설계 대상에서 제외한다.

## B. 원고료 송금 자동화

원고료 캠페인(프리미엄)에서만 발생. 기본 캠페인은 제품 제공이 대가라 송금이 없다.

### 핵심 제약
- **사업소득 3.3% 원천징수**가 법정 의무. 자동 송금하더라도 원천징수·지급명세서 제출은 반드시 남긴다.
- 개인사업자가 은행 API로 임의 자동이체를 붙이는 것은 진입장벽이 높고, 소액 다건에는 과하다.

### 최적안 — 반자동 대량이체 (권장)
1. **지급대장 시트**(11-가이드의 [지급대장] 시트)에 리뷰어별 원고료·계좌를 스크립트가 자동 집계.
2. 스크립트가 **3.3% 원천징수 후 실지급액**을 계산하고, 은행/토스 **대량이체 업로드용 양식(엑셀)**을 자동 생성.
   - 3.3% = 소득세 3% + 지방소득세 0.3%. 실지급 = 원고료 × 0.967.
3. 운영자는 그 파일을 **인터넷뱅킹/토스 비즈니스 "대량이체"에 업로드 → 한 번에 송금**. (건별 계좌입력 0회)
4. 이체 후 시트에 "지급완료+일자" 기록, 분기별 원천세 신고·지급명세서는 이 대장 그대로 세무 대리인에게 전달.

### 더 자동화하려면 (규모가 커질 때)
- **토스페이먼츠/페이플 "정산·지급대행 API"** 또는 **세무 플랫폼(삼쩜삼 비즈, 자버 등)의 3.3% 자동원천징수+지급**: 계좌 등록 후 API로 지급하면 원천징수·지급명세서까지 자동. 월 지급 건수가 수십 건을 넘어설 때 도입 검토.
- 그전까지는 **"스크립트가 대량이체 파일 생성 → 운영자 업로드"**가 비용 0원의 최적점이다.

### 하지 말 것
- 현금·개인 계좌 임의 송금(원천징수 누락) → 매출 커지면 세무조사에서 전액 추징.
- 리뷰 대가를 "송금"이 아니라 "구매대금 환급"으로 포장 → A-2와 동일한 위법.

## C. 리뷰 완료 확인 자동화 (가장 자동화 효과가 큰 영역)

리뷰어가 URL을 제출하면, 검수의 **기계적 부분**을 스크립트가 대신 본다. **대가표시 확인은 최종적으로 사람이** — 이게 우리를 지키는 법적 방어선이라 자동화에 100% 위임하지 않는다.

### 파이프라인
```
리뷰어 URL 제출(폼/1:1)
   → 구글시트에 적재
   → Apps Script 자동 점검(아래 5종)
   → '자동검토 결과' 열에 ✅/⚠️ 표시 + 사유
   → 운영자는 ⚠️만 눈으로 확인 → 최종 '검수통과' (admin.html/시트)
```

### 스크립트가 자동 점검하는 5종
1. **URL 유효성**: 200 응답 & 네이버 블로그/인스타 도메인인지.
2. **지정 키워드 포함**: 제목·본문에 캠페인 키워드가 있는지(본문 텍스트 fetch 후 문자열 검사).
3. **대가표시 문구 후보 탐지**: "제공받아", "협찬", "원고료" 등 표시 문구가 있는지 **1차 스크리닝**. → 있으면 ✅후보, 없으면 ⚠️(사람이 반드시 확인). *표시 위치·명확성 판정은 사람 몫.*
4. **분량**: 본문 글자수 ≥ 기준(예 1,000자).
5. **검색 노출 확인**: **네이버 검색 오픈API**로 캠페인 키워드 검색 → 제출 URL이 상위 N개에 들어오는지 자동 확인(발행 24~48시간 후 재실행). 광고주 리포트 수치도 여기서 자동 수집.

### 구현 메모
- 네이버 블로그 본문은 iframe 구조라 단순 fetch로 본문이 안 잡힐 수 있다 → 모바일 URL(`m.blog.naver.com`)로 정규화 후 fetch하면 텍스트 확보율이 높다. 인스타는 비공개·로그인 벽이 있어 **URL 유효성까지만 자동**, 내용 검수는 사람이.
- 네이버 검색 API는 무료 쿼터로 충분(일 25,000회). `datalab`/`search` 오픈API 키 발급만 하면 됨.
- 이 파이프라인의 ⓐ URL 적재 → ⓑ 자동 점검 → ⓒ 리포트 수집은 11-가이드의 Apps Script에 함수로 추가한다(다음 확장 시 `checkSubmissions()` 신설).

### 왜 완전 자동 통과를 안 하나
대가표시 누락 1건이 공정위 신고로 이어지면 광고주가 떠나고 업체가 박제된다. 스크립트의 "문구 있음"은 **있는지**만 보지 **명확한 위치·크기인지**는 못 본다. 그래서 스크립트는 **의심 건을 걸러 사람에게 넘기는 필터**로만 쓰고, 최종 승인 도장은 사람이 찍는다.

## D. 자동화 우선순위 (도입 순서)

| 순위 | 자동화 | 효과 | 난이도 | 도구 |
|---|---|---|---|---|
| 1 | 리뷰 URL 자동 점검 5종 (C) | 검수 시간 최대 절감 | 중 | Apps Script + 네이버 API |
| 2 | 배송 리스트 자동 생성 (A-1) | 반복 취합 제거 | 하 | 구글시트 함수 |
| 3 | 마감 리마인드 다이제스트 | 독촉 누락 방지 | 하 | Apps Script(11-ⓑ 이미 설계) |
| 4 | 원고료 대량이체 파일 생성 (B) | 송금 실수·원천징수 누락 방지 | 중 | Apps Script + 뱅킹 대량이체 |
| 5 | 검색 노출 리포트 자동 수집 (C-5) | 광고주 리포트 자동화 | 중 | 네이버 검색 API |

**공통 원칙**: 카톡은 사람이 말하는 채널로 두고(자동 발송은 알림톡 심사 후 규모 커질 때), 데이터·판정은 시트/대시보드/스크립트가 처리한다. **"스크립트가 준비하고 사람이 원클릭"** — 이게 이 사업의 자동화 최적점이다.
